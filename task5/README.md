# Проектирование GraphQL схемы на основе REST API

## 1. Анализ существующего REST API

На основе Swagger-контракта можно выделить три ключевые сущности:

- Client — основная сущность клиента
- Document — документы клиента
- Relative — родственники клиента

API предоставляет три отдельных endpoint-а:

- Получение клиента по ID
- Получение документов клиента
- Получение родственников клиента

### Недостатки текущего подхода

- Данные разнесены по разным endpoint-ам
- Для получения полной информации требуется несколько запросов
- Возникает проблема избыточных вызовов (N+1)
- Клиент не может выбрать только необходимые поля

---

## 2. Подход к проектированию GraphQL

GraphQL позволяет:

- Объединить связанные данные в одну структуру
- Избежать дублирования API
- Дать клиенту возможность выбирать только нужные поля
- Сократить количество сетевых запросов

Основная идея — сделать Client агрегирующей сущностью, включающей связанные данные.

---

## 3. Определение сущностей

В GraphQL выделяются следующие типы:

- Client
  - id
  - name
  - age
  - documents
  - relatives

- Document
  - id
  - type
  - number
  - issueDate
  - expiryDate

- Relative
  - id
  - relationType
  - name
  - age

Связи:

- Client содержит список документов
- Client содержит список родственников

---

## 4. Определение запросов (Query)

Вместо нескольких REST endpoint-ов используется один основной запрос:

- Получение клиента по ID

Через него можно получить:
- только данные клиента
- документы
- родственников
- любую комбинацию этих данных

---

## 5. Покрытие REST API

Все существующие операции REST покрываются одним GraphQL-запросом:

- Получение клиента
- Получение документов
- Получение родственников

GraphQL позволяет объединить их в один вызов, что устраняет необходимость делать несколько отдельных запросов.

---

## 6. Преимущества полученной схемы

- Уменьшение количества сетевых вызовов
- Отсутствие дублирования endpoint-ов
- Гибкость в выборе данных
- Упрощение клиентской логики
- Лучшая расширяемость
