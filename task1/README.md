# Архитектура масштабирования и отказоустойчивости

## 1. Стратегия масштабирования

### Горизонтальное масштабирование (основное)
- Используется Kubernetes (HPA, Cluster Autoscaler)
- Масштабирование:
  - по CPU / memory / RPS
- Позволяет выдерживать рост нагрузки и геораспределение

### Вертикальное масштабирование (вспомогательное)
- Используется ограниченно (возможно для БД/stateful сервисов)
- Ограничено физическими ресурсами

---

## 2. Зоны доступности и ЦОД

- Используются **несколько ЦОД в разных регионах**
- Каждый ЦОД как отдельная зона отказа

---

## 3. Kubernetes конфигурация

### Подход: Multi-cluster

- Отдельный Kubernetes-кластер в каждом ЦОД

### Причины:
- Изоляция отказов (network / cluster failure)
- Нет зависимости от latency между регионами
- Исключение проблем с etcd (split-brain)
- Соответствие high availability требованиям

---

## 4. Балансировка нагрузки

### Подход: DNS-based GSLB + health checks

### Алгоритм:
- Latency-based routing (основной)
- Failover routing (резервный)

### Health checks:
- Проверка доступности:
  - Ingress / LoadBalancer endpoint
  - `/health` endpoint приложения
- При падении:
  - DNS исключает кластер из ответа

---

## 5. Failover стратегия

### Подход: Active-Active (между регионами)

- Все регионы одновременно принимают и обрабатывают трафик
- Пользователь направляется в **ближайший (по latency) кластер**
- Обеспечивается одинаковое время отклика независимо от географии

### Распределение трафика:
- DNS (GSLB) с latency-based routing
- Все кластеры находятся в активном состоянии

### Failover:
1. Health check фиксирует недоступность одного из регионов
2. DNS исключает его из выдачи
3. Трафик автоматически перераспределяется на оставшиеся регионы
4. Пользователи продолжают работу без заметной деградации

### Преимущества:
- Нет "холодного" standby
- Минимальное время переключения (зависит от DNS TTL)
- Соответствие SLA 99.9% и требованиям по latency

---

## 6. Конфигурация базы данных

### Проблема Active-Active:
- PostgreSQL в классическом виде не поддерживает multi-master без компромиссов
- Нельзя просто сделать "active-active" запись в одну БД из разных регионов

### Выбранный подход: Single-Writer + Read Replicas

#### Архитектура:
- 1 регион — **Primary (write)**
- Остальные регионы — **Read replicas (read-heavy)**

#### Как обеспечивается low latency:
- Все read-запросы обслуживаются локально (в регионе пользователя)
- Write-запросы идут в primary регион

#### Репликация:
- Streaming replication (async)
- Возможна небольшая задержка (eventual consistency)

---

### Failover БД:

1. При падении primary:
   - Выполняет failover
   - Один из standby становится новым primary

2. Переключение:
   - Обновление connection string / service discovery
   - Приложение начинает писать в новый primary

3. Соответствие требованиям:
   - RTO ≤ 45 мин — за счёт автоматического failover
   - RPO ≤ 15 мин — за счёт WAL и репликации

### Ограничения и компромиссы:

- Write latency выше (межрегиональные запросы)
- Возможна устаревшая read-данные (replication lag)
- Нет полноценного active-active на уровне БД

---

## 7. Шардирование БД

### Решение: НЕ используется (на старте)

Причины:
- Усложняет архитектуру
- Увеличивает сложность транзакций
- Не требуется на начальном этапе

### Альтернатива:
- Read replicas
- Scaling через вертикальное + реплики
