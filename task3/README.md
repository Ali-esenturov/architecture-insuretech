# Анализ текущего решения и предложение по улучшению архитектуры InsureTech

## 1. Проблемы и риски текущего решения

### 1.1 Синхронная агрегация в `ins-product-aggregator`
- Каждый запрос инициирует вызовы ко всем страховым компаниям
- Время ответа растёт линейно с увеличением числа интеграций
- Высокая вероятность таймаутов
- Один медленный или недоступный провайдер замедляет весь ответ

**Риски:**
- Cascading failure
- Увеличение latency


### 1.2 Зависимость от внешних API
- Нет контроля над SLA страховых компаний
- Ошибки и задержки на стороне провайдеров
- Отсутствует изоляция вызовов

**Риски:**
- Нестабильность всей системы
- Массовые ошибки при деградации одного провайдера


### 1.3 Pull-модель обновления данных
- `core-app` обновляет данные раз в 15 минут
- `ins-comp-settlement` раз в сутки

**Проблемы:**
- Устаревание данных
- Несогласованность между сервисами
- Пиковая нагрузка из-за cron-задач


### 1.4 Синхронное взаимодействие между сервисами
- `ins-comp-settlement` запрашивает данные у `core-app` через REST

**Проблемы:**
- Жёсткая связность
- Таймауты и ошибки сети
- Нет гарантии доставки


### 1.5 Отсутствие кэширования в `ins-product-aggregator`
- Агрегация выполняется на каждый запрос

**Риски:**
- Избыточная нагрузка
- Плохая масштабируемость


### 1.6 Ожидаемый рост количества страховых компаний (от 5 к 10)
- Удвоение количества внешних вызовов
- Рост числа ошибок и времени ответа

**Риски:**
- Ухудшение производительности
- Повышенная нестабильность

---

## 2. Ключевая идея решения

Переход от **Pull + синхронные REST-вызовы** к **Push + Event-Driven архитектуре**

---

## 3. Предлагаемая архитектура

### 3.1 Изменение роли `ins-product-aggregator`

**Было:**
- Синхронная агрегация на лету
**Станет:**
- Асинхронный сборщик + Publisher событий

**Новый поток:**
1. Сервис получает данные от страховых компаний (по расписанию)
2. Агрегирует и сохраняет в свою БД
3. Публикует событие:

```json
{
  "event": "ProductCatalogUpdated",
  "timestamp": "..."
}
```

### 3.2 Ввод Event Streaming

Использовать брокер сообщений Apache Kafka (или аналог)

Топики:
`product-catalog-updated`
`insurance-created`


### 3.3 Обновление core-app и ins-comp-settlement

**Было:**
- Периодический polling через REST
**Станет:**
- Подписка на события

**Поведение:**
- Получают событие ProductCatalogUpdated
- Обновляют локальные реплики данных

**Преимущества:**
- Почти realtime обновление
- Нет cron-задач
- Равномерная нагрузка

### 3.4 Замена синхронного взаимодействия

**Удалить:** ins-comp-settlement -> core-app (REST)
**Заменить на:**
- core-app публикует событие
```json
{
  "event": "InsuranceCreated",
  "data": { ... }
}
```
- ins-comp-settlement подписывается и обрабатывает события

**Результат:**
- Снижение связности
- Устойчивость к сбоям
- Гарантия доставки (при корректной настройке)

### 3.5 Изоляция внешних API

**Добавить:**
- Circuit Breaker
- Retry с backoff
- Timeout
- Bulkhead

**Результат:**
- Изоляция проблемных провайдеров
- Повышение устойчивости

4. Transactional Outbox

**Где применять:**
- ins-product-aggregator
- core-app

**Почему:**
- Гарантия консистентности между БД и событиями
- Исключение потери сообщений

**Принцип работы:**
- Данные сохраняются в БД
- Событие записывается в outbox-таблицу
- Отдельный процесс публикует событие в брокер


5. Что решает предложенная архитектура

**Устраняет:**
- Таймауты между сервисами
- Каскадные падения
- Пиковые нагрузки

**Обеспечивает:**
- Почти real-time обновления
- Масштабируемость
- Устойчивость к сбоям внешних систем

**Готовит к росту:**
- Простое добавление новых страховых компаний
- Отсутствие влияния на latency
